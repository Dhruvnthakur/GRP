# Portfolio mode

Audience: recruiters, hiring managers, interviewers, professors, contributors. The README must answer within the first screen: What is this? Why does it exist? How does it work? What tech was used? How do I run it? What did the developer actually build?

Priority order: 1 clear description, 2 visual demo (existing assets or marked TODO), 3 key features, 4 architecture, 5 tech stack, 6 easy installation, 7 technical challenges, 8 results (only if real), 9 roadmap, 10 author.

- "Technical challenges" and "what I built" must come from code and git history (e.g. a nontrivial module, a custom pipeline) or from the user. If unknown, ask the user a short question set instead of inventing narrative.
- Never inflate scope, scale, users, or performance. A modest honest README beats an impressive false one.
- Author section: only details the user provides or the git config already exposes publicly in the repo; ask before adding links.
- Suggest, don't fabricate, the missing pieces: screenshot locations, a short demo GIF, a results table the user can fill with real numbers.
